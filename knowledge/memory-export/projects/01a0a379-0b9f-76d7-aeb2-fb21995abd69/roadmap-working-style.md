Do not edit or build roadmap files while still brainstorming/critiquing structure. Only create or modify deliverables once the user gives an explicit go-ahead (e.g., "let's go ahead," "draft a first cut"). Work section-by-section: present a take, let the user react/adjust, then move to the next section.

**Why:** User stated this explicitly up front ("Don't start editing when we are brainstorming first iron out things only when given proper instructions you should go ahead and edit") and it held throughout a multi-turn roadmap-building session on 2026-07-06.
**How to apply:** When starting a new roadmap/strategy artifact, default to discussion and critique first. Don't create the file until told to.

Stay at roadmap altitude, not spec/design altitude. When reviewing a business bet or initiative, name the initiative, its metric home, type, and timing — don't design exact UX flows, exact rejection-reason taxonomies, or precise security-control wording unless asked. User corrected me mid-session ("No need to go too deep into exact design and decision parts I guess we are creating a roadmap").

**Why:** Roadmap-level review got derailed into feature-design specifics (interim security guardrail wording, reject-reason categories) that belonged in a PRD, not a roadmap.
**How to apply:** When critiquing an initiative, keep it to: what it is, why it matters, what metric it moves, Build/Discovery/Pilot, rough timing, and any genuine scope/capacity risk. Push design-level detail into a one-line flag at most, and only elaborate if the user asks.
