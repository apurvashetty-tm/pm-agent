1 The problem

ACOM manually cold-calls every dropped cart. Capacity-bound, expensive, and it leaves a large pool of recoverable revenue untouched.

Coverage gap

Of ~17,000 eligible carts/month (patient + address on file), only ~10,000 are attempted — ~40% never called.

Low conversion

Only ~5% of assigned leads convert (lead-assigned → order-placed), human-only baseline.

Expensive

~₹50L monthly cost (payroll + variable telephony/ops) → ~20,000 orders = ~₹250 CPO.

Poor connectivity

Packet loss on the current line degrades conversations and wastes agent time.

2 The approach

A reusable voice-bot qualification-and-routing layer, Ring AI as first vendor. The bot qualifies; humans convert.

Bot qualifies, human converts

AI voice handles first-touch at scale, labels intent Hot/Warm/Cold; only worthwhile leads reach an agent.

Two ways to reach a human

Live transfer when an agent is reliably free; Async callback as the safe default and fallback.

Vendor-agnostic

Ring sits behind a thin adapter → Truemeds-owned normalized outcomes. Future vendor = a mapping, not a rewrite.

Truth stays with Truemeds

Bot payload is a snapshot; every outcome is re-validated against the latest order/cart before any agent action.

ELIGIBLE — the cart must clear every gate

patient_id present+ address_id present+ >30 min idle since last cart change+ platform / city / pincode filter+ AOV ≥ threshold+ frequency cap / cooldown ok+ not placed · not DNC+ within traffic % / concurrency→ ELIGIBLE ✓

All gates are Ops-configurable (M3). The 30-min idle after the last cart change is the dropped-cart trigger.

BOT_OWNED — the Ring AI call (per BRD bot workflow)

Call initiated from Truemeds DID→ Connect handling retry busy/no-answer · scheduled · max attempts→ Agentic layer problem ID → rebuttal/resolution → convince → intent→ Classify Hot / Warm / Cold→ Capture intent · objection tag · summary · transcript · recording

Inputs: personalized variables (name, cart, MRP/SP/discount, address parts, ETA…) + the FAQ/objection knowledge base. Guardrails: no medical advice / substitution / Rx claims.

NORMALIZE + validation — vendor result → safe routing

Ring raw status→ Adapter normalize CONNECTED_HOT/WARM/COLD · CALLBACK_REQUESTED · NOT_CONNECTED · INVALID_NUMBER · DO_NOT_CALL · VENDOR_FAILED · ANALYSIS_PENDING→ Latest-state validation placed? · cart empty? · cart/address/payment/order changed?→ Route priority · manual-validation · suppress · callback · retry

A vendor event is a signal, not truth — we re-fetch the live order/cart before any agent action.

LIVE TRANSFER — only when a human is reliably free

Hot + staffed hours→ Admission control dedicated Ozonetel queue · max-wait/fail-fast · Ops concurrency→ Connected → HA screen-pop · latest cart · CLI
fail-fast →No HA / timeout → priority callback

Conditional (M2b) — built only if M1B telephony discovery is green. Order-validity is validated at screen-pop in V1 (pre-transfer check is V2).

PRIORITY CALLBACK — how the async queue is ordered

Validated Hot/Warm→ Priority score intent → SLA/recency → AOV → requested time→ Ordered queue→ Agent calls back

Default order intent → SLA/recency → AOV; weights + the Hot callback SLA are Ops-configurable (M3). Scheduled callbacks are honored first.

4 Milestones

MVP = M1 + M2a (async). Live transfer (M2b) is additive & conditional — never blocks/delays the MVP; async stays the mandatory fallback.

M1A · Build foundation build

Why first: everything depends on dispatching a call, getting a reliable result back, and switching off safely.
  • Eligible-cart selection, trigger call, context snapshot
  • Store call ID; mark bot-owned; prevent duplicate assignment
  • Normalize outcomes; kill-switch; event logging; linking key

M1B · Discovery gates discovery

Why: decides whether live transfer is feasible before we build it.
  • Telephony model: Truemeds DIDs + Ozonetel queue?
  • Is CLI preserved on transfer? (decides screen-pop)
  • Transfer events + recording across both legs?

M2a · Validation + async routing async MVP

Why re-validate: the call takes minutes; the cart may change or the order may already be placed.
  • Re-fetch latest state; suppress placed/empty; flag changes
  • Route Hot/Warm; handle Cold/no-connect/DNC
  • Show bot context; capture agent disposition

M2b · Live transfer conditional

Why conditional: a failed transfer is worse than a clean callback.
  • Availability gate: queue + fail-fast + staffed hours + concurrency
  • Order-validity gate: at screen-pop
  • 6 go/no-go entry criteria; clean callback fallback

M3 · Config & control ops

Why: rules change constantly; Ops needs safe knobs without an eng change each time.
  • Enable/disable, concurrency, traffic %, filters, frequency caps
  • Live-transfer eligibility + queue controls; fallback SLA
  • Audit, dashboards, anti over-call / queue-starvation guardrails

6 Vendor-agnostic architecture ENGINEERING

Core ACOM never sees vendor specifics. Ring lives behind an adapter that emits Truemeds-owned normalized outcomes; a future vendor is a new adapter mapping, not a core rewrite.

The boundary is the whole point: swap or add a vendor by changing the adapter, with zero change to ACOM routing.

7 Truemeds ⟷ Ring interaction model ENGINEERING

Two directions, both through the adapter. We call Ring for commands (sync); Ring webhooks us for events (async). Polling is a reconciliation backstop only. A vendor event is a signal, not truth — we re-fetch latest state on receipt.

Guardrails: only a hardened, authenticated webhook is exposed to the vendor; no internal order/cart APIs in V1.

⚙ Telephony / live-transfer path ENGINEERING

The hybrid model: Ring keeps its own media path for the bot leg, but dials from a Truemeds-owned DID and transfers a Hot call into an Ozonetel queue — so the handoff is in-platform (CLI preserved, transfer events native). To validate in M1B.

If discovery shows CLI isn't preserved on the transferred leg, screen-pop falls back to a minimal transfer-metadata push (see PRD M2b).
